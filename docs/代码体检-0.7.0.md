## 一、先说袋口：两个「环」，只有一个是物理的

台面袋口由三层东西叠出来，容易混为一谈：

| 层      | 位置                                                                   | 是什么                                | 参与物理？                  |
| ------ | -------------------------------------------------------------------- | ---------------------------------- | ---------------------- |
| ① 视觉环  | `src/table.js:101-108` `TorusGeometry(throatR+0.003, 0.005)`，y=0.003 | 浮在台面上方 3mm 的一圈深色圆环，只是描边            | **否**，纯装饰              |
| ② 收口方块 | `src/layout.js:243-270` `pocketRingBoxes()`，12 段/袋                   | 把 12.5cm **方形**开口填成 **圆形**，顶面与台面齐平 | **是**，球会撞到它            |
| ③ 喉口半径 | `src/constants.js:18` `pocketThroat: 0.048`                          | 圆洞半径 48mm（直径 96mm），决定球心进洞的判据       | **是**（`pockets.js:91`） |

**真正压低进球率的是 ③ + ②，不是 ①**。①只是让你"看见"了那个圆。  
那个"减少首次击球进球率"的机制其实是 `RULES.breakMaxPots`（袋口盖板），2026-09-16 已默认关掉  
（改成 0，因为会死锁，见 `constants.js:161-176`），和这个环没有关系。

### 袋口现在有多紧（对比真实 9 尺台）

|               | 直径      | 球心可通过余量  | 1m 距离的角度容差 |
| ------------- | ------- | -------- | ---------- |
| 本作（角袋/中袋同一个值） | 96 mm   | ±19.4 mm | **1.11°**  |
| 真实 9 尺台 角袋    | ~114 mm | ±28.4 mm | 1.63°      |
| 真实 9 尺台 中袋    | ~127 mm | ±34.9 mm | 2.00°      |

结论：**角袋比真实紧 32%，中袋紧 44%，而且两者一样大**。  
`constants.js:362` 里"喉口留给方向误差的余量只有约 1.1°"就是这个数 —— 玩家的体感是"瞄得挺准却弹出来"。

### 连带影响（改袋口前必须知道）

开球进袋率对袋口尺寸极敏感，而 `BREAK_SHOCK` 的参数面很陡（`constants.js:113-126`）：  
`sideBias 0.68 / fanAngle 98 / shiftX -0.17` 是原袋口下扫出来的好区。  
**袋口一放大，单颗球进袋率会跳，必须用 `test/sweep-break.mjs` 重扫这三个参数**，否则会回到  
"总是那两颗球进"或"每杆进 1.5 颗"。

## 二、游戏 / 玩法层问题（按影响排序）

### G1. 没有杆法（旋转）系统 —— 最大的玩法缺口

`src/shot.js:20-25` 出杆时只给固定前旋 `roll = 0.6`，玩家只能控制**方向和力度**。  
真实台球的走位靠高杆/低杆/侧旋，这里完全没有：打完一颗球，白球去哪全靠运气。  
后果：① 玩家技术天花板很低，练不出"走位"；② 人机 AI 也算不出走位（`ai.js` 只选"当前能不能进"）；  
③ 第四阶段联机做起来也没深度。这是唯一一个"改一次能显著提升可玩性"的点。

### G2. 袋口偏紧且角袋/中袋同尺寸

见上一节。中袋入射角本来就更刁，再和角袋同宽 → 中袋几乎不敢打。

### G3. 袋口形状是"圆洞 + 填角"，不是真实袋口

真实袋口是两段斜库边（jaw）夹一个后部圆弧，球会"咬口"再掉。现在是方形开口被 12 段方块填成圆弧：  
球撞到填角会像撞柱子一样弹开（`layout.js:243-270`）。这是"袋口看着怪、弹得也不像"的根因。  
彻底改要动库边断开方式 + 收口几何，工作量明显大于 G2。

### G4. 单机模式没有犯规体系 ✅ 已完成（2026-10-30）

<p style="color:green">✅ <b>已完成（2026-10-30）</b>：双人/人机侧新增三项犯规罚则 —— 空杆、打错球组、击球后没进袋，
每项都是「不罚，只换人（默认，与旧行为一致）/ 判罚手中球」两档。实现：`duo.js` 的
`DUO_FOUL_PENALTY` 表 + `#activeFoul` 判定（优先级：白球落袋 &gt; 打错球组 &gt; 空杆 &gt; 没进袋；
白球首次触球由 `sim.js` 的 `onCueHit` 回调登记，开放台面不判、清完自己球组后碰黑八合法）。
规则设置同步拆成三级页：`设置 → 规则设置`（hub 两张卡）→「单人模式规则」（球体设置）/
「双人对战规则」（分组判罚 4 项 + 犯规罚则 3 项）。验证：`testDuoFouls` 12 条断言 +
launcher 端到端（[14] 段）全绿；犯规罚则默认全部「不罚球」。</p>

原问题记录（已解决）：

只有"白球落袋"和"提前打黑 8"两个判定（`modes.js:176`、`main.js:506`）。  
空杆、打错组、击球后没碰库（真实规则里的三大犯规）一律无惩罚，也没有提示。  
双人模式里"打错球"只是换人（`duo.js:290-303`）。

### G5. 自由球模式让走位失去意义

`modes.js:60-68`：每一杆开球前都能把白球摆到任意位置。作为"练习/开挂"体验是成立的，  
但它和"想练走位"的目标正好相反 —— 习惯之后打正常模式会很难受。建议至少在 HUD 上标明这是  
"练习模式"，或加一档"只在白球落袋后可摆"。

### G6. AI 只会进攻，不会防守，也不会走位

`ai.js` 调 `planAutoShot` 只按"这一杆能不能进"评分（`auto-aim.js` 的评分权重 wCut/wPot/wCue），  
没有"打不进会不会把球留在袋口"、"打完下一杆还有没有球打"这两项。  
困难/极难档的表现是"它很准，但不像高手"—— 因为它不会做安全球，也不会为下一杆留位。  
（用户在 0.6.0 已经把它调到 30/45/70/91% 的进球率，短期够用；等 G1 做完再升级才有意义。）

## 三、物理 / 手感层

### P1. 滚动阻力用「线性阻尼」近似，不是真实台球模型 ✅ 已完成（2026-10-30）

<p style="color:green">✅ <b>已完成（2026-10-30）</b>：改为「恒定减速度 + 轻阻尼」混合模型 ——
`PHYS.ball` 置 `linearDamping: 0`，由 `sim.js` 新增的 `applyRollFriction(bodies)` 每个物理步手工施加
`dv = (rollDecel + rollDamp·v)·dt`（rollDecel 0.35 / rollDamp 0.10）。
<b>真正的"长台重"主因是 angularDamping 0.9 把自转杀得太快、球全程滑动</b>，已降到 0.15 让球真正滚起来。
实测（撞击初速 → 总行程，括号内为旧值）：1 m/s 4.6m (1.3) · 4 m/s 8.8m (3.9) · 6 m/s 11.3m (5.4) ——
长台行程约翻倍，接近真实"大力杆满台跑"的体感。连带完成：`AUTO` 力度反解改用解析摩擦模型
（`stopDist`/`speedForDistance`，二分 40 迭代），删除 cueDecel/ballDecel 两条直线补丁；
`BREAK_SHOCK`/`RACK` 在新物理下全参数重扫（新组合 sideBias 0.60 / fanAngle 104 / shiftX −0.19，
200 次满力开球终验：平均进袋 0.96、半边空 12%、单球最高 17%）；自动瞄准 throw 补偿下调
0.13 → 0.12（新物理自转保持更久、实际 throw 变小），命中率 3 种子聚合 94.1%（门槛 92%）。</p>

原问题记录（已解决）：

`constants.js:58` `linearDamping: 0.42` 是**指数衰减**（速度每秒乘 e^-0.42），真实台球是近似**匀减速**  
（滚动摩擦 ≈ 0.2~0.3 m/s²）。后果：

- 长台要打得比真实更重（距离与力度不成线性，`AUTO.cueDecel` 那套拟合就是在给这个模型打补丁）；
- 轻推的球"最后一小段突然停住"，不是自然滚停。  
  改成"每步施加恒定减速度 + 保留少量阻尼"更真，但会推翻 `AUTO` 里所有拟合常数（`constants.js:364-385`），  
  属于"想动就一起动"的成组改动。

### P2. 开球靠人工动量重分配（`BREAK_SHOCK`）

`sim.js:108-233` 在白球接触球堆那一刻把动量按扇形重新分配。观感是对的，但它掩盖了引擎对  
密集球堆的处理缺陷，且**参数面极陡**（`sideBias` 从 0.68 → 0.75，单颗球进袋率 13% → 59%）。  
任何改动摆球/袋口/摩擦都必须重扫，这是长期维护成本最高的一块。

### P4. 进袋判定双通道 ✅ 已完成（2026-10-30）

<p style="color:green">✅ <b>已完成（2026-10-30）</b>：`pockets.js` 的 `check()` 已单通道化 ——
主通道 = 球心进 `throatRadiusOf(袋)` 的圆形喉口且 y ≤ 0.9R 开始下沉；传感器只做兜底

建议留一条（球心进喉口 + y 低于阈值），sensor 只做兜底。

## 五、架构层问题

### A1. 没有 git ★ 最高风险

项目从 08-15 至今全部靠 `E:/归档/*.zip` 回退，最近一次是今天的 10-29。  
0.7.0 改动点比 0.6.0 多，一旦改坏只能整包回滚。**开工第一件事建议 `git init` + 首次提交**，  
之后每完成一条 `commit`。zip 归档可以继续留着做里程碑。

### A2. 无 lint / 无类型 / 无 CI

`package.json` 只有 vite / electron-builder / capacitor，没有 eslint / tsc / prettier。  
674 项断言全在本地手动跑。B1 这种"未声明变量"由 eslint 的 `no-undef` 一条就能在保存时抓住。  
最低成本方案：加 `eslint` + `no-undef` + `no-unused-vars`，不追求风格规则。

### A3. `main.js` 1018 行，6 个职责

文件里自己写了"刻意不拆"的理由（`main.js:67-70`），理由成立，但它现在同时装着：  
出杆链路 / 摆球流程 / 落袋计分 / 主循环 / 双人判决落地 / 人机回合状态机。  
第四阶段联机还会加第 7 个。**建议只抽两块**，都是纯状态机、不碰渲染，抽出去还能被无头测试直接跑：

- `ai-turn.js`：`aiPhase/aiPlan/aiT/aiFrom/aiDelta/aiDur` 这 6 个模块级 `let` + `tickAi/aiStartThink/aiFire/aiPlaceStep`
- `duo-flow.js`：`applyDuoVerdict/respotBalls/syncDuo/refreshGhost`（判决 → 台面动作的映射）

### A4. 测试盲区：18 / 35 个模块没有任何测试 import

最要紧的两个：

- **`src/pockets.js`（进袋裁判）零覆盖** —— 它正是历史上出过"球在袋口反复抖、游戏锁死"的地方  
  （`pockets.js:4-12` 记着根因）。现在靠 `test/lib/break-sim.mjs` **另写了一份**进袋逻辑来测，  
  两份实现会漂移：产品里改了阈值，测试仍然绿。
- **`src/shot.js`（出杆链路）零覆盖** —— `test/lib/harness.mjs` 重写了一份出杆，注释说"与 shoot() 完全一致"  
  （`test/suites/ai.mjs:26`），但"完全一致"是靠人保证的，不是靠代码。  
  结论：`npm test` 全绿只能证明"纯逻辑对"，不能证明"游戏里对"。这是 674 项断言最容易被误解的地方。

### A5. 五组常量靠人工镜像，断言只做单向

`prefs` / 双人规则 / 画质 / 声音 / 球组，在 `src/` 和 `public/` 各有一份（启动器是独立静态页，不能 import）：

| 镜像对                                     | 现状                                                        |
| --------------------------------------- | --------------------------------------------------------- |
| `prefs.js` ↔ `launcher.js`              | key 与默认值一致；但 public 侧**不校验 `game`/`diff`**                |
| 双人规则 `duo.js` ↔ `launcher.js`           | 4 个 key 与取值一致                                             |
| 画质 `quality.js` ↔ `launcher-quality.js` | 映射表一致；两边默认对象**都只有 1 个 key**（实际用 4 个）                      |
| 声音 `AUDIO`(constants) ↔ `launcher.js`   | 值一致；`bgm` 白名单在**三处**各写一遍                                  |
| 球组 `rules.js` ↔ `launcher.js`           | **字段名完全不同**：src 是 `{rows,order}`，public 是 `{count,shape}` |

`test/suites/launcher.mjs:232-248` 只断言 `srcKeys ⊆ mirKeys`，不查反向、不比值。  
建议：写一个 vite 插件在 build 时把 `src/constants.js` + 规则表生成一份 `public/shared.js`，  
两边都引它，从"人工同步 + 单向断言"变成"单一来源"。

### A6. 全局单例 + 模块级可变 `let`

`state` 是唯一可变状态树（`state.js`），另有 `main.js:133-143` 的 9 个模块级 `let`  
（`aiPhase/aiPlan/aiT/aiFrom/aiDelta/aiDur/shadowAim/fpsT/fpsN`）。  
不可重入、不能同时跑两局、也不能序列化。第四阶段"服务器权威"要求 session 可序列化/可回放，  
这层现在得改。A3 的抽取正好是第一步（把 6 个 let 收进一个对象）。

### A7. 命名混淆（会持续产生 bug）

- `state.mode` = **视角**（free/tracking/top），`state.modeId` = **玩法**（free/score/limit/…）。  
  只差一个 Id，`getGameMode(state.modeId)` 与 `rig.setMode(state.mode)` 长得几乎一样。
- `GAME_MODES.duo` 既表示"本地双人"，也被 `ai` 用作"走双人规则"的开关（`modes.js:85`）：  
  `gameMode.duo === true` 在代码里**不等于**"本地双人"，而是"有回合制"。  
  实际生效的是 `state.modeId === 'duo'` 与 `mode.id === 'ai'` 这种散落判断（`main.js:999-1001`）。
- `state.modeId` 的注释（`state.js:19`）没有列 `ai`，已经过时。

### A8. 魔法数字散落在模块里，违背「constants.js 是唯一调参入口」

典型：`camera-rig.js` 的补间时长 `0.9 / 0.6 / 0.15`（:264,281,502,562）、  
自由模式缩放极角 `0.55 / 6 / π*0.495`（:393,409）、`aimer.js:22` 瞄准线长 0.55、  
`pockets.js:57,63` 的 0.2 / 0.3、`auto-aim.js:219` 的兜底距离 0.8。  
这些"手感参数"现在改起来要去翻源码。

### A9. 重复实现

`clamp01` ×3、`clamp` ×2、`clampNum` ×3、`MIN_GAP` ×3、`max<min+gap` 顶开 ×4、  
`atan2(x,z)` 方位角约定 ×7（+ 一处相反的 `atan2(z,x)` 在 `sim.js:113`）、  
"球是否活着"判据 ×8、`fmtTime` ×3、进球率 ×2、百分比换算 ×4。  
单条都不致命，但它们让"改一处忘一处"成为常态。

### A10. 无版本迁移策略

存储 key `hmzq.prefs.v1` 靠 `sanitizePrefs` 兜住新增字段（这点做得对），  
但挑战历史的记录结构变化没有迁移路径（`public/history.js` 直接读旧数组）。0.7.0 若加字段要留意。
